About this slide

The model has one job: count two rice pests in photos of light-trap trays. Rice black bug (RBB) and white stemborer (WSB) are each labelled female or male, so four classes are trained. The apps report only the two species, because each sex class must first reach 0.70 mAP50 (a ranking score, see the glossary), and two of them missed that bar in the first run (r18-1). The current model, r50-v5, clears it for all four on validation and on the held-out test split (lowest on test: RBB male, 0.798). The most crowded tray seen held 106 insects, so the model needs room for many boxes per photo. The requirements are in docs/specs/2026-10-13-rice-pest-detector-design.md.

Presenting

Ask why a model might train on four classes but report only two. Pitfall: do not say the model cannot tell the sexes apart; r18-1’s two weak classes missed the 0.70 bar but did not score zero, and r50-v5’s lowest class is 0.826 on validation and 0.798 on test.

Training the model02

Glossary

Ten terms, one line each

Family: one source photo plus all its augmented copies.

dHash: a short fingerprint of an image; similar images get similar fingerprints.

Backbone / head: the part that turns pixels into features / the small last layer that names the classes.

Query: one box slot; the model fills up to 300 per photo.

Mixed precision: doing most maths in 16-bit numbers to train faster.

IoU: overlap of two boxes divided by their combined area; 0.5 counts as a hit.

mAP50: how well confident boxes rank above wrong ones, averaged over classes, with IoU ≥ 0.5.

Threshold: the minimum score a box needs to be counted.

Calibration: making scores honest, so a 0.7 score is right about 70% of the time.

Baseline: the score of a model that does nothing, here “always say zero”.

About this slide

Ten terms recur through the deck. The two that matter most are mAP50, which measures whether confident boxes rank above wrong ones, and calibration, which asks whether a score of 0.7 is right about 70% of the time. A “family” is one source photo plus all its augmented copies, and the baseline is the score of a model that always says zero. Come back to this slide whenever a term is unclear.

Presenting

Point back to this slide whenever a term comes up later. Ask someone to explain the difference between mAP50 and a threshold in their own words. Pitfall: do not read all ten definitions aloud.

The trap

Count families, not files

One source photo → about five augmented copies (some are greyscale). Each square is one file.

copy 1copy 2copy 3copy 4greyscale copy

Split by file: copies land in both train and test. The model has already seen the test photo, slightly altered. Scores go up; real skill doesn't.

Split by family: every copy of a photo stays on one side, so test photos come from source photos the model never trained on.

  • Group files by the name before _jpg.rf.
  • Then catch near-duplicates across families with a perceptual hash (dHash).
  • Keep one copy per family in validation and test.

About this slide

Augmented copies are the trap. If files are split at random, copies of one photo land in both training and test, so the model is tested on a photo it has already seen, slightly altered. Scores go up; real skill does not. The fix is to split by family, so every copy of a source photo stays on one side. Files are grouped by the part of the name before _jpg.rf, near-duplicates across families are caught with a perceptual hash (dHash, a short image fingerprint), and validation and test keep one copy per family.

Presenting

Ask: if a flipped copy of a test photo is in training, is the test still a test? Point out that the split must be checked, not assumed. Pitfall: do not treat the greyscale copies as different photos.

Model choice

Start from a model that already sees objects

RT-DETR-r18vd, then r50vd

A transformer detector (Apache-2.0) pretrained on COCO, a general photo dataset with 80 everyday classes and no insects. Chosen to run on a laptop CPU; the current r50 model takes 1.14 s per photo there.

Transfer learning

Keep the pretrained backbone, which already knows edges, textures and shapes. Swap the 80-class output layer for a new 4-class one and train on trap photos.

300 queries

The model proposes up to 300 boxes per photo. A 100-box model would undercount trays of up to 106 insects.

Pinned

Exact model revision, dataset archive checksum, library versions and random seed are all recorded, so the run can be repeated.

About this slide

The starting model is RT-DETR-r18vd, a transformer-based object detector under the Apache-2.0 licence, pretrained on COCO, a general photo dataset with 80 everyday classes and no insects. This is transfer learning: the pretrained backbone, which already recognises edges, textures and shapes, is kept, and the 80-class output layer is swapped for a new 4-class one trained on trap photos. The model proposes up to 300 boxes per photo, because a 100-box model would undercount trays of up to 106 insects. The first run used the small r18 backbone; later runs use the larger r50. RT-DETR was chosen to run on a laptop CPU, and the current model, r50-v5, takes a median 1.14 s per photo there, under the 5 s gate. Model revision, data checksum, library versions and seed are pinned so the run can be repeated.

Presenting

Ask why 300 queries rather than 100. Likely question: why not train from scratch? Answer: the backbone already knows general shapes, so only the pest-specific part must be learned. Pitfall: the 1.14 s figure is a median of 10 photos on one reference laptop, not a guarantee for every machine.

Pick the metric that matches the job

Two metrics, two different questions

mAP50

“If you sort all your boxes by confidence, do the real insects come first?” Uses every box, at every confidence. Measures ranking, averaged over classes. Needs a box to overlap a real insect by 50% (IoU ≥ 0.5).

Count accuracy

“Is the count per species within ±10% of the truth?” (±1 when fewer than 10.) Uses only boxes above a confidence threshold. This is what an app user sees.

A model can rank well and still count badly, if its threshold is wrong. That is exactly what happened.

About this slide

Two metrics answer two different questions. mAP50 asks whether, when all boxes are sorted by confidence, the real insects come first; it uses every box at every confidence, averages over classes and needs a box to overlap an insect by at least half (IoU ≥ 0.5). Count accuracy asks whether the count per species is within ±10% of the truth, or ±1 when fewer than 10, and uses only boxes above a confidence threshold. That count is what an app user sees. A model can rank well and still count badly if its threshold is wrong, and that is exactly what happened here.

Presenting

Make sure everyone can state the difference: mAP is about ranking, count accuracy is about a threshold. Ask which number someone reading the app would care about. Pitfall: do not call mAP50 “accuracy”.

Treat training code like product code

Silent maths failure

In half precision, the box-matching step could produce infinite costs. Fix: run the matcher and losses in full precision.

Half-written checkpoint

A crash mid-save could corrupt best.pt. Fix: write to a temp file, then swap it in.

Wrong resume

Lost randomness

Resume restarted the random streams. Fix: save and restore all random-number state.

Flattering metric

Count accuracy alone hides a model that counts nothing. Fix: always report it beside the do-nothing baseline.

Bad labels

Timing matters: these fixes came after run r18-1, so r18-1 was trained without them. Run r50-1 (16–17 Oct) was their first GPU run.

About this slide

After run r18-1, one outside review on 14 October and the agent’s own review passes found six problems in the training code. Box matching in half precision could produce infinite costs, so the matcher and losses now run in full precision. A crash mid-save could corrupt best.pt, so saves now go to a temporary file first. Resuming with changed settings is refused by a fingerprint of the config and data, random-number state is saved and restored, count accuracy is reported beside the baseline, and labels with NaN or infinite coordinates are rejected. The fixes came after r18-1, so r18-1 was trained without them; run r50-1 (slide 24) was their first GPU run.

Validation is for choices; test is for one honest look. About this slide

Before wave 2, the low scores were treated as a calibration problem, and a review of run r50-1 guessed they came from how RT-DETR’s loss treats small boxes. That guess was inferred from the library’s design, never measured, and it was wrong. The cause was a bug in transformers 4.57.6: the main loss included the 100 denoising queries, which exist only during training, so box matching could pair real targets with those training-only queries. It was fixed in 5.18. Re-running the same r50 recipe on 5.20.1 (run r50-v5) lifts the highest validation score from 0.31 to 0.94, moves the count-optimal threshold from 0.04 to 0.48, and raises held-out count accuracy from 0.751 to 0.834, above the 0.80 gate on validation. For workshop participants

Six habits from one model

  • Count families, not files. Augmented copies across splits push every score up.
  • Match the metric to the job. mAP measures ranking; the app needs counts.
  • Print the do-nothing baseline next to every number.
  • Look at the raw outputs, then test the explanation. A maximum score of 0.25 explained the zero counts; the cause turned out to be a library bug.
  • Validation for choices, test for one look. Don't spend the test set on a known failure.
  • Review and test training code like any other code: plan, implement, run the tests, fix. The agent drafted it; tests and a reviewer caught its bugs.
