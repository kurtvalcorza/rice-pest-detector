  2. ImplementEdits files, runs commands
  3. Run the testsReads the results and errors
  4. FixGo round again until they pass

Red check first: a new test must fail before the code exists. Green tests are the stop; you still verify.

Coding with AI Agents · Module 1 — Direct

[CORE · 1 min · talk]

About this slide

An agent works in a loop of four steps. It proposes a plan, implements it by editing files and running commands, runs the tests and reads the results and errors, then fixes what failed and goes round again. If you give it no stop condition, it invents one. Passing (green) tests are a checkable stop condition, but not proof the work is right; you still verify. One habit comes before the loop: the red check. When the agent writes a new test, confirm it fails before the code exists, so you know the test can catch a problem.

Tokens and the context window

The model only sees what fits in its context window.

  • Text is split into tokens, pieces of words and code
  • The window holds your prompt, files it read, the conversation so far
  • When it is full, something gets dropped or summarised
Coding with AI Agents · Module 2 — Context

[CORE · 1.5 min · talk]

About this slide

A model does not read a repository the way a person does. Everything it works with is text split into tokens: small pieces of words, symbols and code. The context window is how many tokens it can consider at once. Into it go your prompt, AGENTS.md, every file the agent opened, every command output and the conversation so far. The window is large but finite. When it fills, the tool drops or summarises older material, and details given early can quietly fall out. So point the agent at the files that matter, such as specs/, instead of letting it read everything.

Presenting

Ask: what in this repository would you not want the agent to read in full? A good answer: build folders, virtual environments and run outputs, which the find-callers sub-agent in .claude/agents/ already excludes. Pitfall: do not quote a window size.

Knowledge cutoff

The model learned from data up to a date. Libraries kept changing after it.

  • It may use an old API or an old version’s options
  • It cannot know a package’s latest release unless it reads it
  • Check the docs and your installed versions
Coding with AI Agents · Module 2 — Context

[CORE · 1.5 min · talk]

About this slide

Every model is trained on data up to a date, its knowledge cutoff. Libraries kept releasing versions after that, so an agent may confidently call a function that was renamed, or pass an option that was removed, two versions ago. It cannot know a package’s latest release unless it reads it. The fix is ordinary engineering: check the official documentation for the version you actually have installed, and let the tests run against the real library. One secret always goes in: the agent’s own login. So keep secrets out, use a scoped, short-lived login and keep approvals on.

A licence says what others may do with your work, and what they must do in return. Permissive licences such as MIT and Apache-2.0 let anyone use, change, sell or keep the code private, as long as the copyright and licence notice stay with it; Apache-2.0 also asks you to state your changes and grants patent rights from contributors. Copyleft licences such as GPL-3.0 add one condition: if you distribute the software, you release your source under the same licence. AGPL-3.0 extends that to people using your modified version over a network. Creative Commons licences cover data, text and slides; CC BY 4.0 allows sharing and adapting, even commercially, with credit, a link to the licence and a note of changes. Some models carry their own terms, and some bar commercial use. Code with no licence is under exclusive copyright: you may view it, but not copy, change or share it.
